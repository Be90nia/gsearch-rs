## 1. 切片 A（eu8）

### 1.1 定位：「静默吞掉」发生在哪一层（真实证据）

**(a) 客户端侧——不是 gsearch 吞的。** 新增回归锁 `tests/site_qualifier_diag.rs::client_forwards_site_qualifier_verbatim`：假 SearXNG 收到的 `q` 参数原样含 `site%3Agithub.com`（gsearch 的 `urlencode` 把 `:` 编成 `%3A`）：

```
$ cargo test --test site_qualifier_diag client_forwards_site_qualifier_verbatim
test client_forwards_site_qualifier_verbatim ... ok
```

**(b) 实例侧——引擎支持不一 + 引擎会降级。** 真实实例 `http://192.168.89.249:8888`（同一时刻、同一出口 IP，A/B 各一次请求）：

```
q=site%3Agithub.com+rust -> n_results: 35 | unresponsive: ['brave', 'duckduckgo web', 'google']
q=rust+async             -> n_results: 34 | unresponsive: ['brave', 'google']
```

引擎健康时 `site:github.com rust` 的 35 条**全部落在 github.com**（27×github.com + 4×gist + 3×docs + 1×api）→ 限定符**生效**；但引擎降级时同一查询 0 条（早前 16:3x 的实测：`site:github.com rust` → `n_results: 0`，`unresponsive_engines` 列出 brave/ddg definitions/duckduckgo/duckduckgo web/google/google cse/yandex 共 7 个，理由全是 timeout / too many requests）。

**结论：用户看到的「`site:` 查询 0 结果 = 该站没这内容」有两种成因，都不是 gsearch 的锅**——① 不支持 `site:` 的引擎把限定符静默吞掉（当普通词搜）；② 支持 `site:` 的引擎正超时/限流。客户端无法区分，也不该假装能。

### 1.2 为什么不给「N 个引擎」

派单要求「N 若拿不到就别编」。**拿不到**：SearXNG 的 JSON 响应只给 `unresponsive_engines`（`[["brave","timeout"], …]`）——那是「这次引擎没答上来」，**不是**「引擎忽略了 `site:`」；拿它的个数当 N 是拿代理信号冒充语义属性（实测两者数量还不稳定：同批查询 6 个 vs 7 个 unresponsive）。故文案写「**部分引擎**」，并在代码注释与 README 里写明为何不报数。

## 2. 切片 B（0qw）

### 2.1 复现与定位（不猜）

**(a) 重定向到文件——当前树不产生 0 字节。** 本地回环伺服 150KB 大页面：

```
$ ./target/debug/gsearch.exe fetch http://127.0.0.1:8731/big.html --max-chars 100000 --allow-private > f.txt 2> e.txt
f.txt bytes: 100113        e.txt bytes: 0
$ ./target/debug/gsearch.exe fetch http://127.0.0.1:8731/big.html --max-chars 100000 --allow-private 2>&1 | tee g.txt > /dev/null
g.txt bytes: 100113
identical bytes: True | len a= 100113 len b= 100113
```

**重定向与管道的产物逐字节相同** → 派单里「redirect 与 tee 行为不一致」的归因在当前树**不成立**。

**(b) 那个「10s」是什么。** 盲测八（2026-10-09）当时的 fetch 客户端**硬编码**了 10 秒超时：

```
$ git show f84d131^:src/fetch.rs | grep -n "TIMEOUT"
23:const FETCH_TIMEOUT_SECS: u64 = 10;
```

→ H 的「触发 10s timeout」= **gsearch 自己的客户端超时**，不是外部 kill、也不是缓冲问题。超时发生在**产物产生之前**（body 都没读完）→ stdout 无内容可写 → 「0 字节」。同一时刻第二次跑（站点快了）就拿到 24581 字节——两次观测不是同一状态（且两条命令写的是**同一个文件名**，`> file` 会先截断）。**结论：原报告的「stdout/stderr 缓冲与 timeout 互作用」是误归因**（载荷不支持该结论）。

**(c) 当前树的现状。** 超时已放宽为 30s 默认 + `--timeout 1..=300` + `--retry 0..=3`（`f1c9607` FixG11）；`flush_stdout()` 已在每条产物后显式 flush（`f84d131`）——但**没有回归测试**锁住它（`g8-fix-receipt.md` 的 e2e 只写了「字节数差异 < 5%」这种软判据）。

- **零结果的诊断覆盖所有零结果态**（`no_results` / `filtered_empty` / `searxng_degraded`）——`degraded`（源故障）时主线诊断已是「基础设施降级」，追加的 site: 解释属**次要可能**（文案用「可能」措辞，不冒充主因）。若 PM 认为该态应保持单一诊断，把 `main.rs:684-691` 的条件收窄到 `healthy_empty` 即可（一行改动）。

- **批量 fetch 仍是「收齐再打印」**（md 形态的 meta 头需要全量统计）→ 中途被 kill 仍可能一条都不落盘；改增量打印会动输出契约（meta 头），本轮不做。
